# Lease-before-spawn: the crash-window orchestration and what each fence proves

**Scope.** Gate item 2 (Issue `#18`), phase 6 of the spike. Implementation:
`src/claude_org_runtime/control_plane/session_binding.py` (the staged binding)
and `src/claude_org_runtime/supervisor/session_orchestrator.py` (the walk).
Durable halves: `tests/gate_item2/`, the `session-start` cases in
`tests/fault_injection/`, and the schema constraints in
`tests/control_plane/test_spike_schema.py`. Unmediated characterisation:
`investigation/i18-crash-window-characterisation.md`.

**Status: spike scaffold, throwaway by default (D-0026).** The tests are the
durable half. Q-0001 stays open — `binding_phase` is a spike expression of the
injection seams, not the real schema.

---

## 1. Two different claims, two different mechanisms

The design review that preceded this work made one distinction mandatory, and
it is kept throughout: **the fencing token proves protected writes; the spawn
gate prevents a second model turn.** They are not the same claim.

- **The fencing token** (S6, `docs/lease-fencing.md`) orders *writes*: a stale
  writer's row never lands, and the refusal is durable. It cannot, by itself,
  stop a process that already exists from taking a model turn — a `claude -p`
  child takes no token (`session_provider_child_process` in the destination
  register enforces nothing).
- **The spawn gate** is the ordering this module adds: no provider verb that
  can create or resume a process is executed except between two fenced writes
  under a live lease. That is what makes "the losing claimant is never
  spawned" hold for the shapes the provider is known to admit.

## 2. The walk, and the four injection points

```
acquire(lease)                                    -- epoch up; old tokens dead
   |            <- P1: kill before the binding commit
prepare_binding      (fenced INSERT, phase 'prepared')   -- the admission
mark_spawned         (fenced UPDATE, phase 'spawned')    -- the write-ahead
   |            <- P2: kill between the commit and the spawn
provider.start(--session-id <uuid>)                      -- the external effect
   |            <- P3: kill between the spawn and the read-back commit
post_spawn_gate      (fenced UPDATE on run)              -- the validation
await identity read-back (positive, never inferred -- D-0027)
confirm_identity     (fenced UPDATE, phase 'identity_confirmed')
   |            <- P4: kill after the read-back commit
```

"After the read-back" (P4) is defined as **after `confirm_identity` committed**
— never as "the answer was seen in memory". The UUID is generated by the
orchestrator and passed verbatim as `StartRequest.session_id`; the C2 provider
canonicalises a UUID to itself, so one string is the binding row, the
`--session-id` argument, and the identity that must read back. No C2
derivation function is imported above the provider (D-0009).

`mark_spawned` is a **write-ahead**, committed before the verb: `'prepared'`
durably means *no spawn was attempted*, so recovery never has to guess in the
one window where guessing would mint a second process.

## 3. The spawn-admission critical section, honestly bounded

A claimant executes the provider verb only between the admission write and the
post-spawn validation, both fenced. Two shapes follow:

- Stopped (or dead) **before its admission write** — the return hits a raised
  epoch, the write is refused, the refusal is an `action` row, and the loser
  never becomes a process. This is F3's crash window mediated: the retry that
  lands inside the provider's ~2–3 s admission window (re-measured, not
  assumed — see the characterisation) takes the lease first, and the dead
  claimant's token can admit nothing.
- Stopped **inside the critical section** (admission committed, lease lost
  before the `exec`) — the process can come to exist. SQLite cannot make an
  `exec` transactional with a commit (`ACCEPTANCE.md` §2), so this window is
  not claimed closed: the next fenced write — the post-spawn validation, or
  the read-back commit itself (the walk's final step is *always* a fenced
  write; a phase that needs no confirm still ends in a fenced gate, so a
  claimant whose binding was moved by the takeover is refused rather than
  returned as success) — detects the stale token, and the loser then acts
  **coordinated with the holder, never blind**: while no takeover writer has
  confirmed the run's binding, the loser stops its just-created child at once;
  once one has, a session-level stop could kill the *winner's* adopted worker
  (a stop cannot name a process generation), so the loser stands down and
  surfaces its possibly-rogue process as an unresolved hazard.
  `LoserTerminated` carries all of it without overstatement: whether a stop
  was attempted (`stop_attempted`), the provider's own verdict on it
  (`stop_confirmed` — an unconfirmed stop is reported as unconfirmed, never
  as a termination that happened), and the measured detection→stop latency.

## 4. The recovery protocol (resolve first, resume only, adopt when alive)

A restarted supervisor, in order: **(1)** acquire the lease — raising the
epoch, which is the instant the previous claimant's authority ends; **(2)**
read the run's binding from SQLite alone (D-0001); **(3)** resolve the
existing process *before* any verb that could create a second one:

| Binding found | Provider knows the session? | Action |
|---|---|---|
| none | — | fresh admission (new UUID); provider-side leftovers under other identities are *not* adopted |
| `prepared` | — | continue from `mark_spawned`: the write-ahead proves no spawn was attempted |
| `spawned` / `identity_confirmed` | no | the spawn never ran (the provider commits its own record before `Popen`): re-run it under the **same** committed identity |
| `spawned` / `identity_confirmed` | yes | `resume` — never a fresh `--session-id` claim (U28: the dead session still holds it). The provider's resume adopts a surviving child without spawning; a dead one is reconciled first, then resumed with `--resume` |

Exactly-one is two halves: *at most one* is the schema's partial unique index
(`session_one_active_binding_per_run`); *non-empty* is asserted after every
recovery, by the orchestrator and by the harness invariant
(`one-binding-per-run`) — an index alone cannot say that recovery found
anything.

## 5. What is tested where

- `tests/gate_item2/test_orchestrator_walk.py` — the mediated shapes against a
  scripted provider that refuses nothing: U27 and U32 mediated, the stopped
  claimant returning on both sides of the admission write *and* during the
  read-back stall (simulated deterministically: the injected clock advances
  past expiry and the epoch is raised at the exact seam a stopped process
  would resume from; no real `SIGSTOP` is sent), recovery at all four points,
  orphan non-adoption, durable refusals, and the honest stop verdict on an
  unconfirmable termination.
- `tests/gate_item2/test_session_driver_harness.py` — the session driver's own
  battery (its substitute for the three-role conformance suite): anchor
  reachability, kill-and-recover per injection point, and trace determinism,
  in the default profile.
- `tests/gate_item2/test_mediated_real_provider.py` — the same over the real
  C2 provider and its fake CLI: argv/binding/stream carry one identity;
  supervisor-only kill → adoption without a second spawn; supervisor+child
  kill → `--resume`, never a re-claim; a disagreeing read-back impounded.
- `tests/fault_injection/` (`session_driver`, four `session-start` cases) — a
  real `SIGKILL` at each injection point, restart, and re-identification
  asserted from the reopened database plus the destination's own records
  (live process count per id, single-writer streams).
- `investigation/i18-crash-window-characterisation.md` — the unmediated layer:
  the hazard live on this machine, this CLI. No figure from it is a constant
  in any test (U34).

## 6. Known limits, stated rather than assumed away

- **The admission→exec window is open** and stated (§3). The mitigation is
  detection latency, measured, not a claim of atomicity.
- **A resume of a binding whose provider record died between its own record
  write and `Popen`** recovers through the provider's reconcile-then-resume
  path; a CLI that refuses to resume a never-started session would surface as
  a provider failure, not as a second process. Untested against a live CLI in
  that exact shape.
- **`identity_confirmed` with the provider not knowing the session** is state
  divergence (a wiped provider state root); the walk re-runs the spawn under
  the committed identity rather than minting a new one, and the read-back
  still gates confirmation.
- The orchestrator's `default_identity_confirmation` withholds confirmation on
  `exited-N` readouts (an exit is not an identity); a different provider
  vocabulary needs its own policy, injected at construction.
- The harness's "between commit and spawn" anchor sits after both admission
  writes; the narrower `prepared`-committed-mark-not crash state is exercised
  by constructed rows in the mediated suite, not by a real kill (there is no
  anchor between the two commits, deliberately — the mark is part of the
  admission).
- The stopped-claimant shapes are deterministic simulations (clock + epoch at
  the resume seam); the harness's real signals are the `SIGKILL` cases.
